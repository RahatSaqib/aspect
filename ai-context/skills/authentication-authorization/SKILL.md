# Authentication And Authorization

Use this skill when changing login, JWT/session behavior, Hapi auth scopes, data-access constraints, permission seeds, web routes, menus, or permission-gated React UI.

## Core Model

- Users authenticate through `POST /auth` in `api/src/auth/endpoints.js`, implemented by `authenticate` in `api/src/auth/service.js`.
- Web login sends `clientType: 'web'` from `web/src/store/AuthRedux.js`; mobile clients use `reporter_app` or `true_connect`.
- Access JWTs are generated by `getAccessToken` in `api/src/auth/service.js`. JWT claims include `personId`, `name`, `fullName`, `jobFunctionNames`, `permissions`, `clientType`, and `hasToAcceptLicenseId`.
- Web stores decoded JWT state in the `user` Redux record in `web/src/store/AuthRedux.js`; `AuthProvider` converts it to plain JS and exposes `userPermissions`, `isLoggedOut`, `isCountry`, and `isPakistan` through `useAuthState`.
- `aspectFetch` in `web/src/utils/utils/fetch.js` adds the `Authorization: Bearer <access>` header and logs out on non-login `401` responses.

## Permission Data

Permissions are strings built from `Permission.module` and `Permission.activity`, e.g. `result:view`, `person:edit`, `dashboard:summary`.

Important tables:

- `User`: login identity.
- `Person`: profile, partner, country, and user link.
- `Permission`: `{ module, activity, description }`.
- `JobFunction`: partner-scoped role.
- `JobFunctionPermission`: permissions granted to a job function.
- `JobContext`: assigns a person to a job function and constrains geography/site/disease/assay/device type/tag access.

`getUserPermissions` in `api/src/auth/service.js` loads permissions through:

`Permission -> JobFunctionPermission -> JobFunction -> JobContext -> Person`

Only permissions attached to a job function that the user actually has through `JobContext` are included in the JWT.

To add or change a permission:

1. Add the permission definition to `api/seeds/fixtures/PermissionsDefinition.json`.
2. Add it to the relevant job-function fixture, usually `api/seeds/fixtures/jobFunctionBase.js` or a partner/country-specific fixture.
3. Use existing seed helpers such as `upsertPermissionFixture` and `upsertJobFunctionFixture` from `api/seeds/common.js`.
4. Update API route scopes and web route/menu/UI checks to use the same permission string.
5. Add focused tests for the changed server behavior or permission utility when risk is non-trivial.

## API Authorization

Auth strategies are configured in `api/src/server.js`:

- `clientApi`: JWT strategy for the web/client API.
- `mobileApi`: JWT strategy for mobile API routes.
- `deviceApiKey` and `deviceApiRawAuth`: device authentication.

`validateApi` builds `auth.credentials.scope` from:

- the API family scope (`clientApi` or `mobileApi`),
- each permission module (`device`, `site`, etc.),
- each full permission (`device:view`, `site:edit`, etc.).

Routes are decorated in `api/src/routes.js`:

- `decorateClientAPI(module)` adds `+clientApi` and the module-level auth behavior.
- `decorateMobileAPI(module)` adds `+mobileApi`.
- For module routes, `decorateAPI` also grants higher-level scopes: `admin`, `${module}:admin`, and upgrades `:view` to allow `:edit`/`:admin`, `:edit` to allow `:admin`.
- Use `config.auth = false` only for intentionally public endpoints such as login or password reset.

For endpoint-specific checks:

- Put `auth: { scope: ['module:view'] }` or `auth: { scope: ['module:edit'] }` on the route config.
- Remember Hapi scope syntax: `+scope` means required, `!scope` means forbidden, and unprefixed entries are alternatives.
- Do not rely on web hiding for security; enforce permission scopes on the API route.

## Data Constraints

Permission scopes answer “can this user call this endpoint?” Data constraints answer “which rows can this user see or mutate?”

Use `getConstraints` and `addConstraints` from `api/src/auth/constraints.js` for list/detail/report queries that must respect the user's job context.

Common pattern:

```js
const constraints = await getConstraints(request.auth.credentials);

return query('List things')
  .from('Device as d')
  .leftJoin('Site as s', 'd.siteId', 's.id')
  .modify((qb) => addConstraints(qb, constraints, { device: 'd', site: 's' }));
```

Pass the aliases for the tables present in the query. `addConstraints` can apply partner, geography, site, result, assay, assay type, disease, device type, tag, and person constraints. It returns no rows when constraints are empty.

Do not skip constraints on detail/update/delete handlers just because the route has an auth scope. Validate that the target row belongs to the allowed context before mutating it.

## Web Auth State

Use `useAuthState` from `web/src/hooks/useAuthState.js` inside components wrapped by `AuthProvider`.

Important values:

- `userPermissions`: convenience alias for `jwt.permissions`.
- `jwt.permissions`: decoded permission array/set from the access token.
- `jwt.jobFunctionNames`: decoded job function names.
- `jwt.hasToAcceptLicenseId`: routes user to license flow until accepted.
- `isLoggedOut`: computed from missing/expired JWT.
- `isCountry(code)` and `isPakistan`: country-specific UI helpers.

`web/src/App.jsx` chooses between `App.LogoutApp.jsx` and `App.LogInApp.jsx`. `App.LogInApp.jsx` refreshes tokens, handles idle logout, and defines permission-gated routes.

## Permission Matching In Web

Canonical matching lives in `web/src/oldComponents/shared/requirePermissions.jsx`:

- Exact match: `result:edit` matches `result:edit`.
- Module match: requesting `result` matches any `result:*`.
- Nested level match: `admin` includes `edit` and `view`; `edit` includes `view`.
- `+permission`: required; all required permissions must match.
- `!permission`: forbidden; no forbidden permission may match.
- Unprefixed permissions are optional alternatives; at least one must match when optional permissions exist.

Preferred helpers:

- Use `<PermissionChecker permissions={[...]}>...</PermissionChecker>` for rendering or hiding children.
- Use `const { checkPermission } = usePermissions()` for branching in a component.
- Use `isPermittedUser(userPermissions, { required: [...] })` for route/filter style checks.
- Use legacy `requirePermissions` only when touching existing HOC-based code.

Examples:

```jsx
<PermissionChecker permissions={['person:edit']}>
  <AspectButton>{formatMessage(messages.createNew)}</AspectButton>
</PermissionChecker>
```

```js
const allowed = (required) =>
  isPermittedUser(user.userPermissions, { required });
const canShowAdvancedFilters = allowed(['inventory:edit']);
```

Avoid direct `userPermissions.includes(...)` unless you intentionally need exact-only behavior and do not want module or nested-level matching.

## Routes And Menus

Routes are permission-gated in `web/src/App.LogInApp.jsx` with:

```js
const a = (r) => isPermittedUser(userPermissions, { required: r });
```

When adding a protected page:

1. Add the lazy import in `App.LogInApp.jsx`.
2. Add the `<Route>` under an appropriate `a([...])` permission block.
3. Add or update a menu entry in `web/src/cleanComponents/LoggedInLayout/LoggedInLayout.Navigation.jsx`.
4. Use the same conceptual permission for the route and menu entry.
5. Ensure the backing API endpoint has an equivalent or stricter server-side `auth.scope`.

Menu behavior:

- `getRawLinks(formatMessage, user)` returns top-level links and nested `submenu` arrays.
- Each link has `href`, `label`, `perm`, and optional `submenu`.
- `NavigationMenu` wraps every top-level link in `PermissionChecker`.
- `Submenu` wraps every submenu link in `PermissionChecker`.
- `config.showFormsMenu` can hide the Forms menu independent of permissions.
- Active state is based on exact path for top-level links and `pathname.startsWith(`${href}/`)` for submenus.

For a new menu item, use localized labels from `messages/allMessages.js` or the existing custom-message helper. Do not hard-code user-facing menu text.

## Country-Level Permission Check

`useHasCountryPermission` in `web/src/hooks/person/useHasCountryPermission.jsx` calls `GET /person/has-permission`.

Current API behavior in `api/src/person/hasPermission.js` and `api/src/shared/utilsPerson.js` checks whether the user's job context includes a country-level constraint and whether any associated job function has `person:edit`, `person:admin`, or `admin*` permission. The query parameter is accepted by the endpoint, but the utility currently does not apply arbitrary permission names. Verify the behavior before reusing this hook for non-person permissions.

## Common Pitfalls

- Hiding a React component is not authorization. Always protect the API endpoint too.
- Adding a route without a menu can be valid; adding a menu without a route creates a dead link.
- `module` and `module:view` are not identical in all contexts; understand optional vs required matching before changing checks.
- JWT permissions update on login/refresh. If permission seeds change, users may need to refresh/login again.
- Keep route permission, menu permission, component permission, and API scope aligned unless there is a deliberate stricter rule.
- Do not modify bcrypt dependencies or Node version assumptions; the API runs on Node `14.19.0`.
